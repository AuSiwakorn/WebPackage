## 1. ทำไมต้องทำ

ตอนนี้ระบบรู้แต่ฝั่ง **เงินสดในลิ้นชัก** ฝั่ง **เงินโอน** รู้แค่ว่าบิลไหนจ่ายด้วยการโอน ไม่รู้ว่าเงินโอน **ออก** ไปเท่าไหร่ และไม่รู้ว่าบัญชีของสาขาควรมีเงินเหลือเท่าไหร่

ที่ร้านเจอจริง (จากผู้ใช้):

- **ทอนเป็นโอน** — ลูกค้าให้แบงก์ใหญ่ ร้านไม่มีเงินทอน หรือลูกค้าเป็นบริษัทที่มีนโยบาย **ไม่รับเงินสด** ร้านต้องโอนเงินทอน / เงินคืนให้
- **จ่ายผสม** — ของ 2,000 ลูกค้าจ่ายเงินสด 1,000 แล้วขอโอนอีก 1,000
- **เติมเงินเข้าบัญชีโอน** — สาขาต้องมีเงินในบัญชีไว้โอนทอน / โอนคืน เหมือนมีเงินทอนในลิ้นชัก (ผู้ใช้ขอให้เพิ่มตัวเลือก “โอน” ในฟอร์มเติมเงินทอน / หยิบเงินออก)

**แต่ละสาขามีบัญชีรับโอนของตัวเอง** (ผู้ใช้ยืนยัน) จึงสรุปรายสาขาอย่างเดียว ไม่มีหน้ารวมทุกสาขา

## 2. เป้าหมาย / ไม่ทำ / ต้องไม่เกิด

**เป้าหมาย**

1. บิลเดียวรับเงินสด + โอนได้ และทอนเป็นเงินสดหรือโอนได้
2. ลิ้นชักคิดจาก **เงินสดที่รับจริง − เงินสดที่ทอนจริง** — ทอนเป็นโอนแล้วเงินในลิ้นชักยังตรง
3. **บัญชีโอนของสาขา** นับเหมือนลิ้นชักที่สอง: ยอดยกมา → เปิดร้านกด ตรง / ไม่ตรง → รายการเข้า / ออกระหว่างวัน → ควรมี → ตอนปิดร้านกรอกยอดที่เห็นในแอปธนาคาร → ตรง / ขาด / เกิน → ยอดที่กรอกยกไปเป็นยอดตั้งต้นของวันถัดไป (แบบ ก. ที่ผู้ใช้เลือก)
8. ยกเลิกบิลเลือกได้ว่าคืนเงินลูกค้าเป็นเงินสดหรือโอน — ทั้ง 2 กองตรงกับเงินจริง
4. เติม / หยิบเงินระหว่างวันเลือกได้ว่าเป็นเงินสดหรือโอน
5. รับคืนสินค้า คืนเงินเป็นโอนได้
6. ทุกที่ที่แสดงยอดเงินสด / โอน (ปิดร้าน · ภาพรวมผู้ดูแล · ยอดขายรายวัน · หน้าบัญชี · รายงาน · ใบเสร็จ · Telegram · อีเมลสรุปรายวัน) คิดจากยอดจริงของแต่ละช่องทาง — บิลผสมแยกถูก
7. บิลเก่า / รายงานย้อนหลัง ตัวเลขเท่าเดิมทุกที่

**ไม่ทำ (รอบนี้)**

- ทอนแบบผสมในบิลเดียว (ทอนสด 100 + โอน 500) — ทอนได้ทางเดียวต่อบิล
- หน้ารวมบัญชีโอนทุกสาขา (แต่ละสาขาแยกบัญชี)
- เชื่อมต่อธนาคาร / ดึงรายการจากแอปธนาคารอัตโนมัติ
- หลายบัญชีต่อสาขา · ช่องทางอื่น (บัตร, QR หลายเจ้า)
- ค่าธรรมเนียมโอนแยกประเภท — ถ้ามี ให้บันทึกเป็น “หยิบออก (โอน)” พร้อมเหตุผล

**ต้องไม่เกิด (ถึงจะทำงานได้ก็ถือว่าพลาด)**

- ตัวเลขบิลเก่า / ยอดขายย้อนหลัง / เงินขาด-เกินของวันที่ปิดไปแล้ว เปลี่ยนไปจากเดิม
- ลิ้นชักขาด / เกินผิด ๆ เพราะบิลที่ทอนเป็นโอน
- หน้าใดหน้าหนึ่งยังนับบิลผสมเป็น “เงินสดเต็มยอด”
- ระหว่างอัปไฟล์กับกด Reinstall หน้าขาย / ปิดร้านพัง (ร้านใช้งานจริงทุกวัน)
- ใช้คำว่า admweb / หลังบ้าน บนจอ POS (ติดต่อ = “คนดูแลเว็บ”)

## 5. สิ่งที่ตกลงกับผู้ใช้แล้ว

### 5.1 หน้าขาย — ช่องรับเงิน

```
วิธีชำระ:  [ เงินสด ] [ โอน / พร้อมเพย์ ] [ สด + โอน ]

เงินสด      รับเงินมา [ 1,000 ]   เงินทอน 600
            ทอนเป็น:  ( เงินสด ) ( โอน )    ← ขึ้นเมื่อมีเงินทอน
สด + โอน    รับเงินสด [ 1,000 ]   ที่เหลือโอน 1,000 (คิดให้เอง)
โอน         ไม่ต้องกรอก ยอดเต็มเป็นโอน
```

- ทอนได้ทางเดียวต่อบิล (เงินสดทั้งหมด หรือโอนทั้งหมด)
- **สด + โอน**: กรอกเงินสดที่รับ ระบบคิดส่วนที่โอน = ยอดบิล − เงินสด · ไม่มีเงินทอน
- ใบเสร็จบอกแยก: รับเงินสด · รับโอน · ทอนเงินสด / ทอนเป็นโอน

### 5.2 เติม / หยิบเงินระหว่างวัน (การ์ด “เติมเงินทอน / หยิบเงินออก” ในหน้าเปิด-ปิดร้าน)

- เพิ่มตัวเลือก **เงินสด / โอน**
- เติมแบบโอน = ใส่เงินเข้าบัญชีสาขา (ไว้ใช้โอนทอน / โอนคืน) · หยิบแบบโอน = โอนออกจากบัญชีสาขา (เช่น เจ้าของดึงเงินกลับ, ค่าธรรมเนียม)
- ใช้สิทธิ์ “เงินเข้า / ออกลิ้นชัก” (`cash`) ตัวเดิม · ยังต้องมีเหตุผลทุกครั้ง

### 5.3 รับคืนสินค้า

- คืนเงินเลือกได้ **เงินสด / โอน**
- ใช้สิทธิ์คืนเงินตัวเดิม (`refund_cash`) แต่เปลี่ยนชื่อที่แสดงจาก “คืนเงินสดให้ลูกค้า” เป็น **“คืนเงินให้ลูกค้า”**

### 5.4 บัญชีโอนของสาขา (ลิ้นชักที่สอง — แบบ ก.)

```
ควรมีในบัญชี = ยอดยกมา
             + เติม (โอน)
             + ลูกค้าโอนจ่าย (รวมส่วนโอนของบิลผสม)
             − ทอนเป็นโอน
             − คืนเงินลูกค้าแบบโอน
             − หยิบออก (โอน)
```

- ตอนปิดร้าน กรอก **ยอดคงเหลือที่เห็นในแอปธนาคาร** → ระบบบอกตรง / ขาด / เกิน
- ยอดที่กรอกยกไปเป็นยอดตั้งต้นของวันถัดไป **ทั้งก้อน** (ไม่มีการ “แยกเก็บ” แบบเงินทอน)
- **ตอนเปิดร้าน เช็กยอดยกมา** (ผู้ใช้เลือก 23 พ.ย. — ระหว่างร้านปิดมีเงินเข้า-ออกบัญชีเป็นประจำ เช่น ฝากเงินนำส่ง, เจ้าของโอนออก, ลูกค้าโอนดึก)
  ทำแบบเดียวกับนับเงินทอนยกมาที่มีอยู่แล้ว:
  ```
  ยอดบัญชีโอนยกมา 12,000     [ ตรง ]  [ ไม่ตรง ]
                              └─ ไม่ตรง: ยอดในแอปตอนนี้ [ 15,000 ]  เหตุผล [ ฝากเงินนำส่งเมื่อวาน ]
  ```
  - ไม่ตรง → ยอดตั้งต้นของวันนี้ = ยอดที่กรอก · ผลต่างลงประวัติเปิดร้านเป็น **“เงินขยับระหว่างร้านปิด”** ไม่ไปปนกับขาด / เกินตอนปิดของวันนั้น
- ยอดตั้งต้นครั้งแรกของแต่ละสาขา ผู้ดูแลกรอกในหน้าเพิ่ม / แก้สาขา
- แจ้ง Telegram ตอนปิดร้านบอกบัญชีโอนขาด / เกินด้วย เหมือนเงินสด

### 5.5 การ์ด “สรุปเงินวันนี้” ตอนปิดร้าน

```
┌─ สรุปเงินวันนี้ ─────────────────────────────────┐
│ เงินสดในลิ้นชัก            │ บัญชีโอนของสาขา          │
│ เงินทอนตอนเปิด    1,000   │ ยอดยกมา        12,000   │
│ รับเงินสดจากขาย  +6,200   │ ลูกค้าโอนจ่าย   +8,450   │
│ ทอนเงินสด        −1,350   │ ทอนเป็นโอน        −600   │
│ เติม / หยิบ / คืนเงิน ...  │ เติม / หยิบ / คืนเงิน ... │
│ ควรมีในลิ้นชัก     6,650   │ ควรมีในบัญชี    19,850   │
│ [นับเงินได้จริง]            │ [ยอดในแอปธนาคาร]          │
│                            │ ▸ รายการโอนทีละรายการ     │
└───────────────────────────────────────────────┘
```

- ฝั่งโอนมีรายการทีละรายการ (เวลา · เลขบิล / เลขใบคืน / เหตุผล · เข้า / ออก · จำนวน) ไว้เทียบกับแอปธนาคาร
- ผู้ดูแลย้อนดูสรุปนี้รายวัน รายสาขา (ภาพรวมผู้ดูแล / ยอดขายรายวัน)

### 5.6 บิลเก่า

- บิลเงินสดเดิม = รับเงินสด `received` · ทอนเงินสด `change_amount`
- บิลโอนเดิม = รับโอนเต็มยอด `total`
- ไม่มีการแก้ข้อมูลเก่า ตัวเลขย้อนหลังเท่าเดิมทุกที่

### 5.7 ยกเลิกบิล — เลือกว่าคืนเงินลูกค้าทางไหน (แบบ ข. ผู้ใช้เลือก 23 พ.ย.)

ตัวอย่างที่ทำให้ต้องเลือก: บิล 400 ลูกค้าให้แบงก์ 1,000 ร้านโอนทอน 600 แล้วยกเลิกบิล — ชีวิตจริงร้านคืนเงินสด 400 ไม่ใช่คืนสด 1,000 แล้วให้ลูกค้าโอนกลับ 600

- **ยกเลิกบิล** (ไม่ได้แก้ไข): กล่องยืนยันมีตัวเลือก **คืนเงินลูกค้าเป็น ( เงินสด ) ( โอน )** ยอดคืน = ยอดบิล
  - เงินที่รับ / ทอนตอนขายยังนับตามจริง แล้วหักยอดคืนจากช่องทางที่เลือก
  - ตัวอย่างข้างบน คืนเป็นเงินสด → ลิ้นชัก +1,000 − 400 = +600 · บัญชีโอน −600 (ตรงกับเงินจริง)
- **แก้ไขบิล** (ยกเลิกเพื่อดึงกลับเข้าตะกร้า): ไม่มีตัวเลือก บิลเดิมถอยกลับทั้งใบเหมือนเดิม บิลใหม่บันทึกการรับเงินตามจริง (เงินไม่ได้คืนลูกค้า แค่ออกบิลใหม่แทน)
- ยกเลิกได้เฉพาะบิลของวันที่ร้านยังเปิด (เหมือนเดิม) — เงินคืนออกจากลิ้นชัก / บัญชีของวันนั้นเสมอ

| `stock_store_day` | `bank_carried` decimal(12,2) NULL | ยอดบัญชียกมา (NULL = วันที่เปิดก่อนเปิดใช้ฟีเจอร์ ไม่มีส่วนบัญชีโอน) |
| | `bank_open_counted` decimal(12,2) NULL | ยอดในแอปตอนเปิดร้านเมื่อกด “ไม่ตรง” (NULL = ตรง) |
| | `bank_open_reason` varchar(255) NOT NULL DEFAULT '' | เหตุผลที่ยอดยกมาไม่ตรง |
| | `bank_expected` decimal(12,2) NULL | ควรมีตอนปิด |
| | `bank_counted` decimal(12,2) NULL | ยอดในแอปธนาคารที่กรอกตอนปิด |
| `stock_branch` | `bank_start` decimal(12,2) NOT NULL DEFAULT 0 | ยอดตั้งต้นของบัญชีโอน (ผู้ดูแลกรอก) |

**บิลเก่าไม่ต้องเติมข้อมูล (ทางที่ผมเลือก):** 4 ช่องเงินของบิลเป็น `NULL` = บิลเก่า → อ่านค่าจากของเดิม

```
รับสด    = COALESCE(pay_cash,        IF(pay_method = 'cash', received, 0))
ทอนสด    = COALESCE(change_cash,     IF(pay_method = 'cash', change_amount, 0))
รับโอน   = COALESCE(pay_transfer,    IF(pay_method = 'transfer', total, 0))
ทอนโอน   = COALESCE(change_transfer, 0)
```

- สูตรนี้ต้องอยู่ **ที่เดียว** — ฟังก์ชันใหม่ในโมดูลคืนชิ้น SQL ของแต่ละช่อง (เช่น `Stock_buildPaySql('s')`) ทุก query ที่แยกเงินสด / โอนเรียกใช้ตัวนี้ และ `sale_bill_shape` (`api/sale.php`) เติม 4 ค่านี้ให้บิลที่หน้าเว็บใช้
- ตรวจแล้ว (17 พ.ย.): บิลเงินสดทุกใบตั้งแต่ commit แรกเก็บ `change_amount = received − total` และ `received ≥ total` เสมอ → รับสด − ทอนสด = `total` ของบิลเก่าทุกใบ
- **เปลี่ยน enum ของ `pay_method`** ใช้คีย์ที่ไม่ใช่ชื่อคอลัมน์จริงแบบ `perms_text` (บรรทัด ~79 ของ `database.php`) — ตัวติดตั้งรันทุกครั้งที่ Reinstall (MODIFY ซ้ำได้ไม่เสียหาย) · ถ้าใช้คีย์ `pay_method` จะไม่รันเลยเพราะมีคอลัมน์นี้แล้ว
- บิลใหม่บันทึกครบทั้ง 4 ช่องเสมอ (ช่องที่ไม่มีใส่ 0) · `received` = เงินสด + โอนที่รับ · `change_amount` = เงินทอนรวม (หน้าเดิมที่ยังอ่าน 2 ช่องนี้ยังแสดงถูก)

**ระหว่างอัปไฟล์กับกด Reinstall ต้องไม่พัง:** ทำแบบเดียวกับ `Stock_hasProductOwnerColumn()` (สินค้าของสาขา 22 ต.ค.) — มีตัวเช็กว่ามีคอลัมน์ใหม่แล้วหรือยัง ถ้ายังไม่มี ทุกหน้าทำงานแบบเดิม (หน้าขายมีแค่ 2 วิธีจ่าย, ไม่มีบัญชีโอน) · ลำดับขึ้นเซิร์ฟเวอร์ที่แนะนำ: อัป `database.php` → Reinstall → อัปไฟล์ที่เหลือ

### 6.2 สูตรเงิน (`api/store.php`)

```
ลิ้นชัก   = เงินทอนเริ่มวัน + เติม(สด) − หยิบ(สด) + Σ(รับสด − ทอนสด) − คืนเงิน(สด) − ยกเลิกบิลคืน(สด)
บัญชีโอน = ตั้งต้นวันนี้ + เติม(โอน) − หยิบ(โอน) + Σ(รับโอน − ทอนโอน) − คืนเงิน(โอน) − ยกเลิกบิลคืน(โอน)
ตั้งต้นวันนี้ = COALESCE(bank_open_counted, bank_carried)
```

- Σ นับบิล `status = 'paid'` **และ** บิลที่ยกเลิกแบบเลือกช่องทางคืน (`void_refund_channel` ไม่ใช่ NULL) ของ `day_id` นั้น
- “ยกเลิกบิลคืน(ช่องทาง)” = Σ `total` ของบิลยกเลิกที่ `void_refund_channel` = ช่องทางนั้น
- บิลยกเลิกที่ `void_refund_channel` เป็น NULL (ยกเลิกก่อนเปิดใช้ / ยกเลิกเพื่อแก้ไข) ไม่นับทั้งใบ — เหมือนเดิม ตัวเลขย้อนหลังไม่เปลี่ยน
- ตรวจแล้ว: `bill_void` ยกเลิกได้เฉพาะบิลที่ร้านของวันนั้นยังเปิด → เงินคืนอยู่ใน `day_id` เดียวกับบิลเสมอ
- `Stock_getDayCash` เปลี่ยนเป็นสูตรใหม่ (บิลเก่าได้ผลเท่าเดิมเพราะ รับสด − ทอนสด = `total`)
- ฟังก์ชันใหม่คู่กันสำหรับบัญชีโอน (เช่น `Stock_getDayBank($dayId)`) คืนแต่ละบรรทัดของสูตร + ควรมี
- **ยอดยกมาของบัญชีโอน** (ตอนเปิดร้าน บันทึกลง `bank_carried`):
  1. วันก่อนหน้า (ปิดแล้วเสมอ — `store.php` ไม่ให้เปิดวันใหม่จนกว่าจะปิดวันค้าง) → `COALESCE(bank_counted, bank_expected)` (ปิดย้อนหลังแล้วเว้นยอดในแอป = ใช้ควรมี)
  2. วันก่อนหน้าไม่มีตัวเลขบัญชีโอนเลย (ปิดก่อนเปิดใช้ฟีเจอร์) / ไม่มีวันก่อนหน้า → `bank_start` ของสาขา
- **เริ่มนับบัญชีโอน** ที่การเปิดร้านครั้งแรกหลัง Reinstall · วันที่เปิดค้างไว้ก่อน Reinstall (`bank_carried` เป็น NULL) ไม่มีส่วนบัญชีโอน และตอนปิดไม่ต้องกรอกยอดในแอป
  · `bank_start` = ยอดในบัญชีก่อนเปิดร้านครั้งแรกหลังเปิดใช้ · ผู้ดูแลแก้ `bank_start` ระหว่างที่สาขายังไม่เคยปิดร้านพร้อมตัวเลขบัญชีโอน → `bank_carried` ของวันที่เปิดอยู่ตามค่าใหม่ด้วย (แก้ได้ในวันแรก)
  · ผู้ดูแลลืมกรอก `bank_start` ก็ไม่เป็นไร — เปิดร้านวันแรกพนักงานกด “ไม่ตรง” แล้วกรอกยอดในแอปได้ (ผลต่างลงประวัติ)
  · แนะนำ: อัป + Reinstall หลังร้านปิด แล้วผู้ดูแลกรอกยอดตั้งต้นทุกสาขาก่อนเปิดร้านวันถัดไป

### 6.3 หน้าขาย (`sale.php` · `inc/sale-live.php` · `api/sale.php`)

- 3 วิธีจ่ายตาม 5.1 · `bill_save` รับ: วิธีจ่าย, เงินสดที่รับ, ทอนเป็น (cash / transfer)
- ตรวจฝั่งเซิร์ฟเวอร์:
  - เงินสด: รับมาน้อยกว่ายอด = ไม่บันทึก (เหมือนเดิม)
  - สด + โอน: เงินสดต้องมากกว่า 0 และน้อยกว่ายอดบิล
  - ทอนเป็นโอน: มีได้เฉพาะวิธีเงินสดที่มีเงินทอน
- กล่องยืนยันรับเงิน (`data-confirm="pay"` ใน footer) แสดงรับสด / รับโอน / ทอนเป็นอะไร
- ข้อความหลังบันทึก (`sale_flash`) บอกแยกช่องทาง
- **แก้ไขบิล** (ดึงกลับเข้าตะกร้า): ดึงวิธีจ่ายเดิม + ทอนเป็นอะไรกลับมาเป็นค่าตั้งต้น (`bill_redo` รองรับ `mixed` + ช่องทางทอน) · จำนวนเงินกรอกใหม่ (ยอดบิลใหม่อาจไม่เท่าเดิม)
- **ยกเลิกบิล** (5.7): `bill_void` รับช่องทางคืนเงิน (ไม่ใช่ตอนแก้ไข) บันทึก `void_refund_channel`
  - กล่องยืนยันยกเลิกบิล (`data-confirm="void"` ของบิลใน footer) มีตัวเลือกคืนเป็นเงินสด / โอน · เลือกไว้ก่อน = เงินสด ถ้าบิลมีรับเงินสด ไม่งั้น = โอน
  - ทุกที่ที่ยกเลิกบิลได้ (กล่องแจ้งผลหลังขาย · บิลของฉันวันนี้ · ประวัติขาย ฯลฯ — คนทำไล่หาให้ครบ) ใช้กล่องเดียวกัน
  - ประวัติยกเลิกบิล / Telegram (`notify_on_void`) บอกว่าคืนเงินทางไหน

### 6.4 เปิด / ปิดร้าน (`store.php` · `api/store.php`)

- **เปิดร้าน:** แสดง “ยอดบัญชีโอนยกมา” + ปุ่ม ตรง / ไม่ตรง (5.4) ต่อจากส่วนนับเงินทอนยกมาเดิม · บันทึก `bank_carried` (+ `bank_open_counted` / `bank_open_reason` เมื่อไม่ตรง — เหตุผลจำเป็น)
  - ประวัติเปิดร้าน: ยอดบัญชียกมา · ยอดในแอป · ผลต่าง “เงินขยับระหว่างร้านปิด” + เหตุผล · Telegram เปิดร้าน (`notify_on_open`) บอกด้วยถ้าไม่ตรง แบบเดียวกับที่ทำกับเงินทอนยกมา (ถ้ามี)
- **การ์ดเติม / หยิบ:** ตัวเลือกเงินสด / โอน (5.2) · รายการในการ์ดบอกช่องทาง
  - หยิบเงินสดยังห้ามเกินเงินที่ควรมีในลิ้นชัก (เหมือนเดิม)
  - หยิบ / ทอน / คืนแบบโอน **ไม่ห้าม** แม้เกินยอดที่ควรมีในบัญชี แต่แสดง “บัญชีโอนควรเหลือ N” ให้เห็น (เหตุผลในข้อ 7)
- **ปิดร้าน:** การ์ดสรุปเงินวันนี้ (5.5) · ช่องยอดในแอปธนาคาร (จำเป็น)
  - เงินสด **หรือ** บัญชีโอน ไม่ตรง = ต้องกรอกหมายเหตุ (ใช้ช่องหมายเหตุเดิมช่องเดียว)
  - บันทึก `bank_expected` · `bank_counted` · ประวัติปิดร้านมีบรรทัดบัญชีโอน
- **ปิดร้านย้อนหลัง** (`Stock_closePastDay` — หน้าเปิด-ปิดร้าน + ภาพรวมผู้ดูแล): ช่องยอดในแอปธนาคาร **ไม่บังคับ** ว่าง = ใช้ “ควรมี” ของวันนั้น
- **สรุปหลังปิด** (การ์ด “สรุปการปิดร้าน”) มีแถวบัญชีโอน

### 6.5 รับคืน (`return.php` · `api/return.php`)

### 6.6 หน้าอื่นที่ต้องแสดงยอดเงินสด / โอนจากยอดจริง

ทุกที่ที่ตอนนี้ใช้ `pay_method` / `$b['method']` แยกเงินสด / โอน (ไล่จาก grep ณ 17 พ.ย.):

- `api/sale.php` — `sale_summary` · `sale_flash` · `Stock_shapeBill`
- `api/bill.php` — สรุปเงินสด / โอนของหน้าบัญชี (บรรทัด ~126, ~317, ~333)
- `api/report.php` — รายงาน (บรรทัด ~231)
- `api/notify.php` — ปิดร้าน · อีเมลสรุปรายวัน (ส่วน “เงินสด / โอน แยกช่องทาง”) · Telegram ขาด / เกิน
- `themes/aostock/adm-dashboard.php` — เงินขาด / เกินรายสาขา (เพิ่มบัญชีโอน)
- `themes/aostock/adm-day-sales.php` — ยอดขายรายวัน (+ สรุปเงินวันนั้นของสาขา)
- `themes/aostock/account.php` · `inc/history-past.php` · `return.php` · `inc/sale-bills.php` — ป้ายวิธีจ่ายของบิล: “เงินสด” · “โอน / พร้อมเพย์” · “สด + โอน” (+ “ทอนเป็นโอน” ถ้ามี)
- `themes/aostock/bill-print.php` — ใบเสร็จ (5.1)

**ยอดเงินสด / โอนในรายงานยอดขาย** = สุทธิของแต่ละช่องทาง (รับ − ทอน) — บิล 400 ที่รับสด 1,000 ทอนโอน 600 → เงินสด +1,000 · โอน −600 · รวม 400 (ยอดรวมเท่ายอดขายเสมอ)
· รายงานยอดขายนับเฉพาะบิล `paid` เหมือนเดิม — บิลยกเลิกแบบเลือกช่องทางคืน (5.7) มีผลแค่สูตรลิ้นชัก / บัญชีโอน ไม่นับเป็นยอดขาย

### 6.7 ผู้ดูแล

## 9. ทดสอบ

ในเว็บทดสอบในเครื่อง (Apache :8098 / MariaDB :3399 — สร้างใหม่ได้ถ้า Temp ถูกล้าง)

- บิล 3 วิธี + ทอนเป็นโอน: ค่าที่บันทึก · กรณีปฏิเสธ · ใบเสร็จ · แก้ไขบิลดึงวิธีเดิมกลับ (บิลเดิมถอยทั้งใบ)

- ลิ้นชัก: วันที่มีทอนเป็นโอน ควรมี = เงินในลิ้นชักจริง
- บัญชีโอน: ยกมา (กรณีในข้อ 6.2 + วันที่เปิดก่อน Reinstall + แก้ยอดตั้งต้นวันแรก) · เปิดร้านกด ตรง / ไม่ตรง (+ เหตุผลจำเป็น · ผลต่างไม่ปนกับตอนปิด) · เติม / หยิบแบบโอน · คืนแบบโอน · ปิดร้านตรง / ขาด / เกิน + หมายเหตุ · ยกไปวันถัดไป · ปิดร้านย้อนหลัง
